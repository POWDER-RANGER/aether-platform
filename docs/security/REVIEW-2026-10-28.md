# Security review — 2026-10-28

Scope: read-only inspection of the tooling branch implementation. No security fixes are made here. Findings are limited to inspected files; where runtime behavior was not executed, it is marked unverified.

## 2. Intent key handling

The companion CLI reads `keys/intent.key` directly with `Path.read_bytes()` in `src/aether/cli_ext.py`. The inspected path does not log the key bytes. The key is passed to GovernorClient, which stores it in memory and uses it for HMAC signing. No secure creation/ACL routine or cross-platform permission check was found in the inspected code. Therefore default Windows ACLs and Linux umask-derived permissions are **not verified**; do not assume private permissions. Severity: HIGH. Proposed fix: owner-controlled key provisioning with exclusive create, restrictive POSIX mode (0600), Windows DACL validation, no key in exception/log/manifest, and tests for permissions and redaction. No control code was changed.

## 3. NitroGen pickle boundary

`src/prrex/backends/nitrogen_reflex.py` uses `pickle.dumps` for outgoing request and `pickle.loads(self.sock.recv())` for the incoming response. The socket default endpoint is `tcp://127.0.0.1:5555`; the endpoint is configurable, and this adapter does not itself reject non-loopback endpoints. A comment claiming localhost-only is therefore an assumption, not an enforced guarantee. The public NitroGen server binds wildcard in upstream research notes; do not expose it to untrusted networks. Severity: CRITICAL for untrusted endpoint; HIGH for configurable endpoint. Proposed fix: enforce loopback by default and explicit owner opt-in for other endpoints; use authenticated transport or a non-executable serialization format; validate response schema before use.

Untrusted-byte deserializers found in repository source: the NitroGen response `pickle.loads` call above. The request side serializes via `pickle.dumps` and does not deserialize. No other `pickle.loads` or `pickle.load` call was identified in the inspected source tree. Full exhaustive search is not claimed beyond the branch tree reviewed.

## 4. Recording privacy

`RecordingSession` writes JPEG frames under `frames/`, a frame index, event JSONL, manifest and distinct intended/commanded/delivered/observed/player_input streams. Screen frames can include usernames, notifications, chat, account details or other personal data. No telemetry upload is implemented in the inspected recording/session code; the recorder writes to local paths. This is not a repository-wide proof that no telemetry exists. Severity: HIGH privacy risk if shared. Proposed fix: default local-only storage, owner-set retention period, encrypted-at-rest option, ROI redaction before export, explicit consent, and share gate refusing unredacted frames. Preserve originals privately; redact copies only.
