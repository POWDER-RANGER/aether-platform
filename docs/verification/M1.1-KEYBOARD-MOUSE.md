# M1.1 keyboard and mouse output: verification record

Second peripheral path, built on the M1 control foundation (PR #2). Status words: project instructions §10.

## Design (DECISIONS D-020, D-021)

- `aether.control.kbm.KeyboardMouseAdapter` is an output adapter at the same boundary as the virtual-pad adapters. The Governor still decides every frame; the adapter only translates the normalized action (`GamepadFrame`) into keys, mouse buttons and relative mouse motion through an explicit mapping (`DEFAULT_KBM_MAP`, overridable in settings under `kbm`).
- Kill switch, halt latch, delegation, policy, watchdog and neutral-on-stop apply unchanged; a neutral frame releases every key and button.
- Adapter-level safety: focus gate (keys never land in another window), release before press, release all on close, Windows/menu keys refused, every injected event tagged (`dwExtraInfo = 0xAE7E`).
- Injection: Windows `SendInput` with scancodes.

## MSI hardware runs (`python -m aether kbmtest`)

Own test window; cursor re-centred before each step; keys and mouse buttons read back with `GetAsyncKeyState`, motion with `GetCursorPos`. Default mapping: 18 keys, 2 mouse buttons, 2 mouse axes, plus neutral and a focus-loss check: 26 checks per run.

| Runs | Harness | Result |
| --- | --- | --- |
| 1 | First version | 24/26. Focus-loss check FAILED: a minimized window can stay the foreground window, so the harness still reported focus. Harness fixed (minimized counts as unfocused). One cursor-motion mismatch on a key-only step (LX-, 272 px) |
| 2–6 | Focus fix | Runs 3, 4, 6: 26/26. Runs 2 and 5: 25/26, one cursor-motion mismatch each on a key-only step (LY+ 22 px; LEFT_THUMB 9 px). Focus-loss check passed in all five |
| 7–9 | Adds per-step count of mouse events the adapter sent | Runs 8, 9: 26/26. Run 7: 25/26, cursor moved 1,425 px on LY-, with **zero** mouse events sent by the adapter in that step |
| STOP | Final harness, STOP file after 5 s | Halted; every key and button read back released. Four cursor-motion mismatches before the halt, all with zero adapter mouse events |

Across all 10 runs, every key and mouse-button check matched, and every mouse-axis step moved the cursor in the commanded direction. All mismatches were cursor motion on steps where the mapping produces no mouse output. Where the harness counted (runs 7–9 and STOP), the adapter sent no motion in those steps, so the motion came from another source on the machine (most likely the physical mouse in use during the runs). Runs 1, 2 and 5 predate the counter. The owner confirmed afterwards that he was using the mouse across two screens during the runs and had not been told in time that they were starting (2026-10-26), which accounts for the outside motion. From now on, input-injecting hardware runs start only after the owner confirms the machine is free.
